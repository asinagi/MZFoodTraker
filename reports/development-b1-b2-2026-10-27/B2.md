# B2 — 출처별 Query Planner와 로컬 예산

2026-10-27. B1까지 159개 + B2 신규 40개 = **199개 테스트 통과**, 실패/오류/skip 0, 외부 소켓 시도 0. [summary](b2-tests/test-summary.json). B1은 별도 커밋 `6cece7c0bd9aa9b69b69c9071ab738e811062c67`로 보존했다. B2 커밋·원격 결과는 [최종 Git 기록](git-results.json)을 참고한다.

`query_planner.py`는 HTTP client를 import하거나 호출하지 않는다. `preview()`는 reader만 사용한다. `commit()`은 명시적인 계획·매핑 기록이며 예약, 시도, last_success 갱신 또는 실행 job 생성이 아니다. 결과의 `execution_enabled`는 항상 false다.

## 출력과 버전

각 계획은 query_id, plan_id, source_id, account_scope, query_kind/query_kinds, canonical_query, spec_hash, planner_version, 계약/adapter/policy/cost 버전, FOOD_ID/target 매핑, due_slot, estimated_cost, budget_status, policy_status, effective_window, 계정 설정 fingerprint를 가진다. 원본 contract의 field_states/origin/정책을 재사용한다. 계획의 user/mock origin은 계획 생성 경위이며 미래 실제 관측의 origin을 정하지 않는다.

canonical JSON은 키 정렬·UTF-8·NaN 금지로 직렬화한다. source/account/실제 요청 조건/기간/페이지 상한/버전을 hash에 포함한다. food_id/별칭 ID/target generation은 별도 다대다 매핑에 둔다. 전송 조건이 같은 DISCOVERY/TRACKING도 query를 공유하고 역할을 query_kinds에 보존한다. NAVER 그룹 구성은 실제 요청 조건이므로 hash에 포함한다.

동일 spec은 QUERY를 재사용한다. 같은 query/due_slot/매핑 snapshot/account fingerprint는 같은 PLAN ID를 사용한다. 매핑이나 버전이 변하면 새 PLAN을 생성한다. 이전 QUERY/PLAN/매핑은 UPDATE/DELETE trigger로 보호한다. 같은 request_key/payload의 commit은 기존 응답을 재생하며 다른 payload는 409다. 저장 시점 예산 snapshot은 변경하지 않고 GET 상세의 current_budget/current_validation으로 현재 판단을 별도 제공한다.

## 출처별 계획

| 출처 | 조건과 제한 |
| --- | --- |
| Instagram | 승인된 별칭 중 해시태그 문법에 맞는 명칭만 사용. 공백을 제거해 새 태그를 만들지 않음. `#` 표기·casefold는 기존 Graph adapter의 태그 직렬화 의미로 적용하고 원래 alias_id 매핑 보존. lookup→recent_media 단계, 필드·limit 50·API version·max_pages를 기록. unique tag, lookup call, media page 비용을 분리. 페이지 상한 PARTIAL_LIMITED, 오류 PARTIAL_OR_FAILED는 B3 처리 계약 |
| YouTube | FOOD_ID별 정확 별칭을 개별 q로 사용. 무조건 OR 결합하지 않고 미승인 Boolean 연산자 입력도 제외. KR/ko/date 기본, 지역·언어·정렬·7일 기본 게시 기간·maxResults 50·페이지 상한 보존. videos 상세는 search 결과의 공개 video IDs가 있어야 materialize할 수 있는 별도 dependent template, batch size 50. 검색 일치가 음식 언급을 확정하지 않음 |
| NAVER | 한 FOOD_ID의 승인 별칭을 하나의 그룹으로 묶음. groupName은 대표명 중복과 구별되는 FOOD_ID, food_group_mapping 보존. 5그룹씩 배치, 그룹당 5개 MVP 상한, 그룹 내 중복 제거. 그룹 간 같은 검색어는 관련 그룹을 차단하고 임의 배정하지 않음. 5개를 넘는 별칭은 조용히 잘라 쓰지 않고 검토 사유 반환. 기간·timeUnit·device/gender/ages·그룹 구성 전체가 비교 context |
| RSS | `include_discovery=true`에서 KR 고정 feed 하나만 계획. 음식별 요청 생성 금지. 기본 1800초, 기존 service.interval을 우선. FOOD 0건은 정상. 추적 target과 별개인 DISCOVERY |

YouTube의 기존 광역 발굴 목록은 config에서 유지하며 발굴 계획을 선택적으로 제공한다. 기존 실행 수집기의 query/토큰/상태를 수정하거나 새 planner에 자동 연결하지 않는다. TRACKING/DISCOVERY 결과 모두 음식 추출·파생 분석은 활성화하지 않는다.

기본 YouTube 기간의 끝은 UTC 6시간 슬롯으로 정규화하여 재계획마다 현재 초가 달라져 요청이 증식하는 것을 막았다. 명시적인 기간은 그대로 정규화한다. NAVER는 완료된 KST 날짜를 사용하고 기본 30일이다. IG 슬롯은 계정의 기존 주기, RSS 슬롯은 feed 주기로 정규화한다. 각 target의 정확한 due_at은 따로 보존한다. 미래 예정 target은 미리 볼 수 있지만 NOT_DUE이며 예약/결과 연결 대상에서 제외한다.

요청 예시는 [Mock 인수 시나리오 JSON](acceptance-example.json)의 query_examples와 rss_discovery_example에 전체 canonical 파라미터·hash·단위·매핑을 기록했다.

## 예산 구분과 공식 문서 확인

예산 항목은 source/account/quota_type/provider_reset_timezone/effective_window/local_limit/provider_limit/estimated_cost/reserved_cost/observed_usage/remaining_budget/reservation_status를 제공한다. 공급자의 실제 원격 사용량·잔여량은 모르면 null, provider_usage_verified=false다. READY_LOCAL은 로컬 판단이며 실제 원격 실행 보장이나 수집 성공이 아니다. DEFERRED_BUDGET, NOT_DUE, 정책/권한 BLOCKED를 구분한다.

- YouTube 기존 로컬 상한: search 40회/일, videos 1000회/일. 전달된 기존 config의 더 구체적인 상한을 적용한다. PT 자정과 DST를 사용한다. Windows tzdata 부재 시 기존 adapter와 동일한 2007년 이후 미국 DST 규칙을 사용하며 23/25시간 날짜를 검사했다.
- 2026-10-27 확인한 [YouTube 공식 quota 문서](https://developers.google.com/youtube/data/determine_quota_cost)는 2026-10-15 갱신 기준 search 전용 기본 100회/일·호출당 1 search quota와, 기타 endpoint 공용 10,000 units/일을 구분한다. [search.list](https://developers.google.com/youtube/data/reference/rest/v3/search/list)와 videos.list 비용을 별도 항목으로 둔다. 실제 프로젝트 Cloud quota·다른 앱의 차감량을 조회하지 않았으므로 그 값은 검증 완료로 표시하지 않는다.
- NAVER 로컬 100회/일과 KST 날짜 경계를 유지한다. 공급자 실제 할당량은 미확인이다. [NAVER 공식 검색 트렌드 문서](https://developers.naver.com/docs/serviceapi/datalab/search/search.md)의 파라미터 의미를 확인했지만 기존 adapter는 별도 API HUB endpoint를 사용하므로 인증/계약 동등성을 단정하지 않는다. 공식 공개 문서의 더 큰 그룹당 키워드 상한으로 MVP의 5개 제한을 확대하지 않았다.
- IG의 기존 rolling 7일 고유 태그·soft28/hard30 모델을 유지했다. 기존 instagram_searches와 새 로컬 예약·시도 상한을 합쳐 계산하며 같은 태그 재요청은 최초 7일 창을 연장하지 않는다. [Meta 공식 문서](https://developers.facebook.com/docs/instagram-api/guides/hashtag-search/)는 도구에서 접근되지 않아 최신 조건 재확인 완료로 표시하지 않았다. live policy/permission은 기본 차단이며 Mock에서 기존 모델의 회귀만 검증했다. lookup/media call의 공급자 동적 한도는 미확인이므로 고유 태그 한도와 혼합하지 않는다.

한 번의 preview에서 여러 query가 같은 예산을 모두 사용할 수 있다고 판단하지 않도록 가상 비용을 누적한다. 가상 비용은 메모리에만 있고 예약이나 사용량 기록이 아니다. legacy youtube_calls/naver_calls 및 해당 IG 계정의 기존 검색 기록을 읽어 이미 진행된 로컬 시도를 보수적으로 반영한다.

## 명시적 로컬 예약 계약

UI/API의 preview와 commit은 예약을 하지 않는다. `planner.quota.reserve(plan_id,attempt_key,attempt_no,ttl_seconds)`는 후속 B3를 위한 **내부 Python 계약**이며 public HTTP endpoint로 노출하지 않았다.

reserve는 BEGIN IMMEDIATE에서 현재 정책·권한·generation·food_revision·due_at을 재검증하고, 공유 query/due_slot/attempt_no를 고유화해 동일 논리 요청의 이중 예약과 예산 경쟁을 막는다. TTL은 최대 300초이며 날짜 reset 경계를 넘지 않는다. 만료 기록은 지우지 않고 현재 예산 계산에서 제외한다. 같은 attempt key는 원래 예약을 반환하며 기간을 연장하지 않는다. 이전 예약이 아직 유효하면 다음 시도 예약을 거부한다.

`mark_attempted()`도 현재 조건과 예산을 원자적으로 재검사한다. 앞선 공유 태그 예약이 해제되어 0비용 근거가 사라진 경우를 다시 계산한다. 이미 ATTEMPTED인 비용은 원격 차감 불명 상태라도 환불하지 않는다. release는 실행 시도 전 RESERVED에만 허용된다. 모든 전이는 quota_events에 남는다.

검색 계획 비용은 **워크플로 최대 페이지 수에 따른 상한**이다. B2의 ATTEMPTED는 Mock 또는 로컬 실행 의도 기록이며 실제 HTTP 횟수를 증명하지 않는다. `observed_usage_basis`는 legacy 로컬 call + 기록한 워크플로 상한으로 표시하고, actual_new_http_attempts/원격 사용량은 null로 둔다. B3는 각 실제 HTTP·재시도·페이지와 상세 조회를 materialize하고 실제 시도 원장·공급자 비용을 연결해야 한다. 이 단계의 상한을 실제 수집 결과 수로 표시하면 안 된다.

예약 당시 아직 due가 아닌 target은 snapshot에 넣지 않는다. `valid_result_targets(reservation_id)`는 ATTEMPTED 시점에 포함됐고 지금도 활성 generation/food revision/정책에 맞는 target만 반환한다. 한 target을 pause해도 공유 query의 다른 유효 target은 남는다. HTTP 취소, outbox, lease/fencing, 원격 exactly-once는 구현하지 않았다.

## RSS 로컬 식별 연결

성공한 기존 CollectionService.collect 뒤 현재 회차의 FOOD/REVIEW만 `FoodService.import_rss_run()`으로 넘긴다. 추가 HTTP 없이 기존 A4 정책·공통 후보·정확 별칭 식별을 사용한다. 신규 음식이나 추적 대상을 자동 생성하지 않는다. 이미 존재하는 승인 별칭만 기존 food_id에 연결하고 UNKNOWN/브랜드/불확실 이름은 검토 상태로 남긴다. RSS FOOD/REVIEW 0건이면 공통 후보도 만들지 않는다.

각 run/item의 command key로 재실행을 멱등화한다. bridge 실패는 entity_resolution=pending_retry로 보고하고 이미 성공한 RSS 원본·run을 실패로 재작성하지 않는다. 재처리는 명시적인 `import_rss_run(run_id)`다. 원자적 전달 보장은 B3/B4 과제다. source 유형이 바뀐 재import는 공통 후보를 검토 상태로 되돌리고 SOURCE_TYPE_CHANGED 이력을 남기며 원래 RSS 분류 이력을 수정하지 않는다. 과거 origin을 새 live_api로 승격하지 않는다.

기존 테스트의 assertion을 제거하지 않았다. migration 기대 단계는 현재 버전 범위로, 원래 30개 테이블 비교는 BASE_SQL의 명시적 테이블 목록으로 확장 가능하게 했고, 과거 origin 테스트는 bridge 이전의 실제 legacy 상태를 만들도록 fixture에서 자동 bridge만 막았다. 원래 origin 미승격 assertion은 그대로다.

## 스키마·API·UI

v5는 다음 8개 테이블을 추가한다.

| 테이블 | 역할 |
| --- | --- |
| planner_queries | 고유 source/account/spec_hash와 canonical JSON·버전 |
| planner_plans | query/due_slot/mapping_hash/account fingerprint별 불변 계획 snapshot |
| planner_query_targets | query ↔ target/generation/food_revision/alias provenance 다대다 |
| planner_plan_targets | 계획별 target의 정확한 due_at과 frozen 매핑 |
| planner_commands | 명시적 계획 저장의 멱등성 |
| quota_reservations | plan·공유 query·due_slot·attempt 번호·기한·예약 당시 유효 target snapshot |
| quota_charges | 리소스별 상한 비용·단위·distinct tag·고정 유효 창 |
| quota_events | 예약/시도/해제의 append-only 이력 |

GET `/api/planner/preview?target_id=...`, `/history?target_id=...`, `/plans/{plan_id}`를 제공한다. 읽기는 reader만 사용한다. preview는 여러 target_id 및 기간·지역·언어·NAVER 필터 옵션을 받을 수 있다. POST `/api/planner/preview`도 `{target_ids,options}`를 읽기만 한다. POST `/api/planner/commit`만 `{request_key,target_ids,options}`로 기록한다. 계정 권한·정책 override, 음식 추출 작업, 인증정보·미정의 옵션은 거부한다.

음식 상세의 각 출처에 검색 요청·예산 미리보기, 명시적 계획 기록, 이전 계획 조회를 추가했다. 실제 실행 버튼이나 quota 예약 버튼은 없다. 표시 테마를 유지하며 모바일에서 본문 JSON은 접어서 확인한다. [브라우저 결과](b2-browser-summary.json), [모바일 미리보기](b2-query-preview-mobile.png), [기존 음식 UI 회귀](a4-regression/browser-summary.json).

## 검증과 후속 인수

40개 신규 테스트는 source serializer, 미승인 별칭 차단, 다대다 공유·부분 pause, spec/PLAN 멱등성, 기간/계정/그룹 context, IG 7일 경계·legacy 사용량·soft 한도·예약 해제 경쟁, YT PT/DST, NAVER KST, readonly preview, 예산 부족, immutable 이력·별칭 취소 새 버전, 정책 우회 차단, RSS 고정 feed·로컬 bridge·실패 재처리, 예약/상태 경쟁·기한·환불 금지·늦은 결과 차단·버전 무효화를 다룬다.

[Mock 인수 예](acceptance-example.json)에서 FOOD 0 상태의 두쫀쿠 등록→승인→세 출처 대상→6개 계획→preview 쓰기/예약 0→명시적 기록→Mock 예약 계약→YouTube pause→늦은 음식 매핑 0·이력 보존을 확인했다. 외부 소켓을 차단했다.

운영 사본 0→5 검증에서 원래 30개 테이블의 원래 열/행 해시가 일치했고 FK 오류 0, integrity ok, 재실행 적용 0, 생성자/조회 변경 0이다. 운영 DB에는 적용하지 않았다. [사본 결과](b2-copy-migration.json).

B3는 [인수 계약](B3_HANDOFF.md)을 따라 실제 lease/fencing·outbox·HTTP 시도와 예약을 연결해야 한다. 기존 수집기와 새 executor를 동시에 같은 요청에 활성화하면 안 된다. provider 권한·실제 quota 확인, 계정 scope의 실제 자격 증명 연결, 각 HTTP 비용/legacy 원장의 중복 회계 방지, 성공/부분/실패 및 다음 스케줄 확정이 선행되어야 한다.
