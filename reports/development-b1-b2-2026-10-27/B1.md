# B1 — 공통 추적 대상과 스케줄

2026-10-27. 기존 141개 + B1 신규 18개 = **159개 통과**. 실패/오류/skip 0, 외부 소켓 시도 0. [테스트](b1-tests/test-summary.json), [격리 Chrome UI](b1-browser-summary.json), [원래 30개 테이블 migration 대조](b1-copy-migration.json).

`TrackingService`는 HTTP client나 scheduler thread를 생성하지 않는다. 승인된 공통 FOOD_ID를 기준으로 `(food_id, source_id, account_scope)` 고유 대상을 만든다. 대표명·여러 별칭은 같은 FOOD_ID를 재사용하며 기존 출처 전용 ID를 공통 ID로 해석하지 않는다.

v4 `tracking_schema.py`가 `tracking_targets`, `tracking_commands`, `tracking_events`, `tracking_slots`를 추가한다. 목표 필드는 target_id/food_id/source_id/account_scope/alias_scope/status/generation/interval_seconds/next_due_at/last_success_at/origin/registration_method/candidate_id/food_revision/revision/created_at/updated_at이다. events는 삭제·변경을 막고 전후 상태·검토자·근거·command key를 보존한다. slots는 작업 예정 메타데이터이며 실행 가능한 HTTP job이 아니다.

상태는 PENDING→명시 승인 ACTIVE→PAUSED/BLOCKED/STOPPED다. PAUSED/BLOCKED의 재개도 명시적 승인을 요구한다. STOPPED는 일반 register/activate/resume으로 복귀하지 않는다. `reregister=true`와 현재 revision을 사용하면 같은 ID가 PENDING으로만 돌아간다.

모든 변경은 request_key/payload 멱등성과 BEGIN IMMEDIATE, optimistic revision 검사를 사용한다. pause/stop/주기 변경/활성화/재개/refresh는 generation을 증가시킨다. 동일 시각의 경쟁 상태 변경은 한쪽만 성공하며 다른 쪽은 409다. 주기 변경은 UTC now+interval, 재개는 UTC now로 next_due를 정한다. 놓친 예정 회차는 schedule에서 한 슬롯만 만들고 next_due를 now 이후로 전진시켜 과거 작업 폭주를 피한다. last_success_at은 이 단계에서 갱신하지 않는다.

음식은 ACTIVE·음식 kind·RESOLVED 공통 후보가 있어야 한다. 브랜드/매장/미승인 후보, RSS의 음식별 tracking source 등록을 차단한다. 수동 등록 origin=user와 DISCOVERY 후보의 실제 origin을 구별하며 이후 API 관측 origin은 건드리지 않는다.

계정 `Account`는 서버가 주입하는 비밀 없는 권한·정책·설정 계약이다. UI/쓰기 API는 configured/permission_verified/policy_allowed를 바꿀 수 없다. 기본 live 계정은 권한·정책이 미확인인 상태로 차단한다. 자격 정보가 없으면 설정 대기 PENDING을 만들 수 있지만 ACTIVE 계획은 불가하다. 검증에서는 명시적인 Mock 계정만 허용했다. 기존 성공 기록으로 현재 인증정보의 권한을 추정하지 않는다.

GET은 저장 상태와 별도로 effective_status/blockers/planning_eligible을 계산한다. 음식 revision 변경·병합·별칭 취소·계정 권한 변경을 발견하면 쓰기 없이 즉시 계획 부적격으로 본다. 별칭 변경은 `refresh`가 food_revision과 generation을 갱신해야 다시 사용할 수 있다. 과거 generation의 결과는 `valid_mapping(db,target_id,generation,food_revision)`에서 거부한다. 실제 실행 중 HTTP 취소나 lease/fencing을 구현한 것은 아니다.

API:

- GET `/api/tracking/accounts`, `/targets?food_id=...`, `/due`, `/events?target_id=...`.
- POST `/api/tracking/register`: food_id, source_id, account_scope, 선택 alias_scope/interval_seconds/candidate_id.
- POST `/api/tracking/activate|pause|resume|stop|interval|refresh|schedule`: target_id, expected_revision. interval에는 interval_seconds, activate/resume에는 approved=true.
- 모든 쓰기에 request_key/actor_ref/reason. local Host·Origin·JSON·입력 필드 제한 유지.

기본 IG 3600초, YT 21600초, NAVER 86400초를 사용하되 실제 전달된 기존 config의 주기를 우선한다. YT 최소 21600초, NAVER 최소 86400초는 기존 MVP 제한이다. IG는 기존 config와 동일하게 양수 주기를 허용한다. UTC 저장·KST 표시이며 현재 B1은 API 예산 자체를 예약하지 않는다.

음식 상세에 출처별 계정·상태·주기·다음 예정·차단 원인·등록/승인/일시 중단/재개/종료/별칭 갱신 UI를 추가했다. 기존 provider 페이지와 수집기는 수정하지 않았고, 새 추적 대상이 기존 수집기로 자동 전달되지 않는다. Chrome에서 세 Mock 출처 등록·활성화 및 pause/resume/stop/reregister를 검증했다.

운영 DB는 v0이며 변경하지 않았다. 기존 listener 8000/8002는 유지했다. 보존 사본의 임시 복제본 0→4에서 원래 열·행 해시 일치, FK 오류 0, migration 재실행 적용 0이었다. 운영 적용에는 writer 조정·최신 백업·명시적 migration·별도 재시작 계획이 필요하다.

A4~A5는 `510bf75`로 별도 커밋했다. 원격 Push는 자동 승인 검토가 첨부 요청서의 지시를 원격 main 변경 승인으로 인정하지 않아 거부했다. 우회하지 않았다. B1은 로컬 독립 커밋으로 보존하고 원격 반영은 별도 승인 전까지 보류한다. 최종 커밋 해시는 전체 보고서에 기록한다.
