# 종합 유행 점수 제안서 — 비활성, 확정 전 구현 금지

**상태: 미구현.** 앱 API v1에는 출처를 합친 점수·순위 필드나 엔드포인트가 없고(`tests/test_app_contract.py`가 검사), 순위는 한 출처·한 지표·한 기간으로만 만든다. 이 문서는 종합 점수가 필요해질 때 결정할 사항을 정리한 제안이다.

## 1. 지금 합치지 않는 이유

| 문제 | 내용 |
| --- | --- |
| 단위가 다름 | RSS는 "급상승 피드에 나타난 트렌드 항목", Instagram은 "해시태그 검색이 돌려준 게시물 중 별칭이 확인된 것". 같은 1이 같은 관심도가 아니다 |
| 관측 범위가 다름 | RSS는 모든 음식이 같은 피드를 공유(SHARED_FEED), Instagram은 추적 중인 음식만 관측(PER_FOOD_QUERY). 추적 여부·해시태그 수·페이지 상한이 값의 범위를 바꾼다 |
| 보존 기한이 다름 | Instagram 캡션 근거 30일, RSS 제한 없음. 30일 이상 기간은 Instagram 값이 대부분 비어 있다 |
| 정책 | NAVER 상대 지수는 저장·누적 금지, YouTube 파생 지표는 비활성. 장기 파생 데이터 보존·재배포 권한은 통합 감사에서 미확인 |
| 근거 없음 | 사람 라벨로 검증한 "실제 유행" 기준 데이터가 없어 가중치를 정할 근거가 없다 |

## 2. 후보 방식 (검토용)

| 방식 | 설명 | 장점 | 위험 |
| --- | --- | --- | --- |
| A. 출처 내 백분위 후 중앙값 | 출처마다 같은 기간 값의 백분위를 구하고, 관측된 출처들의 중앙값을 사용. 기간 전체 관측이 아닌 출처는 제외 | 단위 차이를 없애고 설명이 쉬움 | 출처당 비교 음식 수가 적으면 백분위가 불안정. 추적 편향이 그대로 남음 |
| B. 출처별 변화율 신호 수 | 출처마다 `change.state = COMPARABLE`이고 증가율이 임계값 이상이면 1, 신호 수를 표시(예: "2개 출처에서 상승") | 가장 투명함, 점수가 아니라 근거 개수 | 임계값 근거 필요, 출처 수가 적어 변별력 낮음 |
| C. 정규화 가중합 | 출처별 z-점수(로그 변환)를 coverage 가중으로 합산 | 연속 점수 | 가중치·정규화 근거 부족, 해석 어려움. 현 단계 비권장 |

현 단계에서 하나를 고른다면 **B(신호 수)**가 계약상 가장 안전하다. 점수가 아니라 출처별 근거를 세는 것이라 출처 합산 금지 원칙과 충돌하지 않는다.

## 3. 활성화 전 필요한 결정·작업

1. 출처 정책: Instagram 집계의 공개 앱 재배포·보존 권한 확인, NAVER·YouTube 제외 유지 여부
2. 추적 범위: 비교 대상 음식이 같은 기준으로 추적되는지(Instagram 추적 해시태그 정책)
3. 검증: 사람이 라벨링한 유행 사례로 후보 방식을 백테스트하고 오탐·미탐을 보고
4. 버전: `formula_version`을 응답에 넣고, 바꾸면 이전 값과 비교하지 않음
5. 표시 규칙: 점수와 함께 구성 요소(출처별 값·coverage)를 항상 보여 주고, 기간 일부만 관측된 출처는 제외 사실을 표시

## 4. 확정 시 계약 방향

- v1 순위 API에 필드를 추가하지 않고 별도 엔드포인트(예: `GET /api/v1/trends/signals`)와 별도 스키마로 제공한다.
- 응답에 `formula_version`, 출처별 구성 값, 제외 출처와 사유를 포함한다.
- 계약 변경은 OpenAPI 문서·데이터 사전·계약 테스트를 함께 갱신하는 별도 과제로 진행한다.
